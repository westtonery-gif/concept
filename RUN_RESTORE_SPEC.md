>
> **Это НЕ доменная спецификация.** В отличие от `RUN_SPEC.md` (который описывает только
> предметную область и запрещает детали реализации), этот документ — **реализационный
> контракт уровня SPEC**: он фиксирует *форму*, которой восстановленный Run приводится в
> существование. Архитектурное решение уже принято в **ADR-0015 §3** («архитектура допускает

> решения не вводится** — только реализуемая форма снимка, наблюдения и фабрики.

> атомарность или транзакции — это уровень `RunStore` (инфраструктура, ARCH §9/§10; ADR-0024).

## 1. Назначение и границы

### 1.1. Что фиксирует документ

1. **`RunSnapshot`** — форму *наблюдаемой истины* одного Run: минимальный полный состав, из
   которого восстановленный Run неотличим от сохранённого (RUN_SPEC §4a) и **продолжаемость не
   теряет и не дублирует** уже сделанную работу (ADR-0015 I3).
2. **`Run.snapshot`** — наблюдение: как этот снимок получить от живого Run.
3. **`Run.restore(snapshot)`** — второй вход конструирования Run: приведение агрегата в
   существование прямо в сохранённом состоянии, с применением verify/reject (RUN_SPEC §4a).

### 1.2. Что НЕ входит

- **Механизм сохранения/восстановления, хранилище, сериализация, формат, атомарность,
  транзакции.** Это `RunStore` (инфраструктура; ARCH §9/§10; ADR-0023 §5, ADR-0024).
  `RunSnapshot` — чистое доменное значение (как Views), *persistence-ignorant* (RUN_SPEC §9).
- **Новые доменные состояния, события, переходы, инварианты.** Их нет: восстановление
  переустанавливает уже легально достигнутое состояние (RUN_SPEC §4a; ADR-0015 §3).
- **Реплей журнала событий** — запрещён (ADR-0015 §Rationale; ARCHITECTURE_FREEZE §3). Истина
  авторитетна на сущностях, а не восстанавливается из событий.

### 1.3. Принцип аддитивности

`Run.snapshot` и `Run.restore` — **чисто аддитивное** расширение: `Run.create`, таблица переходов,
`transition` и все существующие сигнатуры/поведение **не меняются** (ADR-0015 I7; PROJECT §4.11;
прецедент ADR-0004…0007). Восстановленный Run — тот же агрегат, достигнутый *иным способом
появления*, не новая сущность.

## 2. Почему View недостаточен (доказанная необходимость снимка)

Наблюдение через существующие read-only View **теряет** часть наблюдаемой истины. Это доказывает
необходимость `RunSnapshot` и одного нового детского типа (`TaskSnapshot`) — а не «сериализуй
Views»:

| Что теряется | Где сейчас | Последствие без сохранения |
|---|---|---|
| `retry_policy` (Task) | `TaskView` **не несёт** | после восстановления граница повторов Task сбрасывается в дефолт — нарушение точности продолжения |
| `rework_policy` (Run) | Run вообще не имеет View | то же для границы доработок Run |
| `task_seq` / `artifact_seq` / `review_seq` / `evaluation_seq` / `analytics_seq` | ни в одном View | **id-коллизия при продолжении**: восстановили Run с `…-task-3`, вызов `open_task` начнёт счётчик с 0 → сгенерит `…-task-1` и **перезапишет** существующего ребёнка. Прямое нарушение **ADR-0015 I3** (без дублирования) |
| журнал `events` | ни в одном View | авторитетная трасса (ADR-0015 I2) потеряна |

**Полны и переиспользуются как есть:** `Output` и `AnalyticsRecord` (frozen, отдаются Run
напрямую), `ArtifactView`, `HumanReviewView`, `EvaluationView` — round-trip-полны. Их поля
покрывают всё приватное состояние своих сущностей.

**Вывод.** Минимально необходимые новые типы: **`RunSnapshot`** (контейнер агрегата) и
**`TaskSnapshot`** (поля Task + `retry_policy`, которых нет в `TaskView`). Artifact / Human
Review / Evaluation / Output / Analytics Record переиспользуются напрямую. Это удовлетворяет правилу
«новых типов — только при доказанной необходимости».

## 3. Состав `RunSnapshot`

`RunSnapshot` — неизменяемое (frozen) доменное значение. Состав — ровно наблюдаемая истина Run,
без чужих данных и без поведения. Все коллекции — кортежи (`tuple`), в порядке появления детей.

**Уровень Run (скаляры и политика):**

- `run_id: str` — идентичность агрегата (RUN_SPEC §3; неизменяемый вход).
- `content_brief_ref: str` — зафиксированный вход (неизменяемый).
- `workflow_version_ref: str` — зафиксированный вход (неизменяемый).
- `status: RunStatus` — ровно один текущий статус (RUN_SPEC §5 инв. 1).
- `rework_count: int` — счётчик итераций доработки (RUN_SPEC §3).
- `failure_reason: str | None` — причина `FAILED`, если достигнут (RUN_SPEC §3).
- `rework_policy: ReworkPolicy` — граница доработок (**не** в View; нужна для точного
  продолжения).

**Продолжение генерации идентификаторов (не в View; обязательны — иначе I3):**

- `task_seq: int`, `artifact_seq: int`, `review_seq: int`
- `evaluation_seq: int` *(1.1 — ADR-0018)*, `analytics_seq: int` *(1.1 — ADR-0020)*

**Состав агрегата (принадлежность, не копии):**

- `tasks: tuple[TaskSnapshot, ...]` *(Output — внутри своего Task)*
- `artifacts: tuple[ArtifactView, ...]` *(переиспользование — View полон)*
- `human_reviews: tuple[HumanReviewView, ...]` *(переиспользование — View полон)*
- `evaluations: tuple[EvaluationView, ...]` *(1.1; переиспользование — View полон; порядок
  значим: «последняя» оценка решает QA-ворота, ADR-0018 §5)*
- `analytics_records: tuple[AnalyticsRecord, ...]` *(1.1; frozen — переиспользование)*

**Журнал (авторитетная трасса; берётся вербатим, не переигрывается):**

- `events: tuple[<любое событие журнала Run>, ...]` — упорядоченная последовательность событий
  Run/Task/Output/Artifact/Human Review/Evaluation/Analytics Record в том же порядке, что и в
  `run.events`.

### 3.1. `TaskSnapshot` (новый тип — единственный среди детей)

Поля `TaskView` **плюс** `retry_policy`:

- `task_id: str`, `run_id: str`, `workflow_step_ref: str`, `agent_ref: str`, `task_input: str`
- `status: TaskStatus`, `attempt_count: int`, `failure_reason: str | None`
- `output: Output | None` *(Output frozen — переиспользование)*
- `retry_policy: TaskRetryPolicy` *(отсутствует в `TaskView`)*

> Размещение: `RunSnapshot` — `domain/run.py`, `TaskSnapshot` — `domain/task.py` (рядом со своими
> View; ADR-0024 §2).

### 3.2. Наблюдение `Run.snapshot` *(1.1)*

- `Run.snapshot -> RunSnapshot` — **read-only свойство**, как `tasks`/`artifacts`: снимок момента,
  не следит за последующими изменениями, ничего в Run не меняет (журнал не растёт).
- Это единственный путь получить политики и счётчики — они приватны. Без него `RunStore.save(run)`
  не мог бы получить снимок (§6), не нарушая инкапсуляцию.
- `Run.restore(run.snapshot)` возвращает Run, неотличимый от исходного (§4.4), и
  `Run.restore(run.snapshot).snapshot == run.snapshot`.

## 4. Контракт `Run.restore(snapshot)`

### 4.1. Сигнатура и роль

- `@classmethod Run.restore(snapshot: RunSnapshot) -> Run` — **второй** вход конструирования,
  наряду с `create`. Не трогает `create`/`transition`/таблицу переходов.
- **Не совершает переход.** Переустанавливает состояние, которого оригинал уже достиг легально
  (RUN_SPEC §4a; ADR-0013). Сторожа переходов не обходятся — они просто не применяются, потому
  что перехода нет.
- **Не эмитит новых событий.** Журнал берётся из `snapshot.events` вербатим; `RunCreated` и
  прочие повторно не порождаются (иначе дублирование трассы — нарушение I2/I3).

### 4.2. Переустановка состояния

`restore` строит экземпляр Run прямо в сохранённом состоянии:

1. Неизменяемый вход (`run_id`, `content_brief_ref`, `workflow_version_ref`) — записывается
   write-once (тем же путём, что `__init__`).
2. Мутабельное состояние (`status`, `rework_count`, `failure_reason`, `rework_policy`, пять
   `*_seq`, журнал `events`) — устанавливается напрямую.
3. Каждый ребёнок (`Task` со своим `Output`, `Artifact`, `Human Review`, `Evaluation`) восстанавливается
   в своё сохранённое состояние **внутренним путём восстановления, доступным только Run**
   (`Task.restore`, `Artifact.restore`, … — как и их конструкторы). Публичной детской фабрики не
   появляется. `AnalyticsRecord` frozen и кладётся как есть.

### 4.3. verify/reject (применение RUN_SPEC §4a)

Восстановленный Run допускается **только** если снимок удовлетворяет инвариантам RUN_SPEC §5.
Нарушение → **доменная ошибка `RunRestorationError`** (подкласс `RunDomainError`), Run **не**
возвращается и **не** устанавливается «как есть». Проверяются структурные инварианты (легальность
проверяется, а не предполагается — §4a), **без** переигрывания истории. Каждая проверка —
инвариант, который путь создания состояния уже обеспечивает; новых правил нет.

1. **Ровно один статус.** `status` — значение `RunStatus`. *(инв. 1)*
2. **Неизменяемый вход на месте.** `run_id`, `content_brief_ref`, `workflow_version_ref` —
   непустые (не из одних пробелов) строки. *(инв. 2)*
3. **Целостность агрегата** *(инв. 7):*
   - у каждого `TaskSnapshot`, `ArtifactView`, `HumanReviewView`, `EvaluationView`,
     `AnalyticsRecord` **и каждого события журнала**: `run_id == snapshot.run_id`;
   - у каждого `Output` (если есть): `task_id` совпадает с `task_id` владеющего Task;
   - каждый `artifact.output_ref` ссылается на `Output`, записанный на каком-то владеемом Task;
   - каждый `artifact.supersedes_ref` (если есть), `review.artifact_ref` и
     `evaluation.artifact_ref` ссылаются на владеемый `Artifact`;
   - каждая `AnalyticsRecord` называет владеемый Task и **его** `agent_ref` (атрибуция выводится
     из Task, ADR-0020 §4) — либо *(1.2, ADR-0036)* владеемую Evaluation и **её** `evaluator_ref`.
4. **Уникальность и связи 1:1** *(инв. 7; DOMAIN_MODEL §2.11/§2.12):*
   - id каждого вида детей (Task, Output, Artifact, Human Review, Evaluation, Analytics Record)
     уникален;
   - Output → Artifact — 1:1: два Artifact не происходят из одного Output;
   - Output есть только у Task в `SUCCEEDED`.
5. **Согласованность счётчиков (защита I3).** Каждый `*_seq` не меньше **числа** детей своего вида
   **и** не меньше **любого порядкового номера**, уже использованного в id этого вида (id,
   сгенерированный Run, имеет вид `{run_id}-{вид}-{n}`; вид — `task`/`artifact`/`review`/
   `evaluation`/`analytics`). Иначе следующий сгенерированный id совпал бы с существующим.
   *(1.1: условие 1.0 «`seq ≥ |дети|`» недостаточно — снимок с единственным `…-task-3` и
   `task_seq = 2` проходил его, а следующий `open_task` перезаписал бы ребёнка.)*
6. **Ограниченность** *(инв. 8):* `0 ≤ rework_count ≤ rework_policy.max_rework_iterations`; у
   каждого Task `0 ≤ attempt_count ≤ retry_policy.max_attempts`.
7. **Терминальность согласована с детьми** *(ADR-0004 §9):* `COMPLETED` Run не владеет
   нетерминальным Task.

**Не проверяется** (сознательно — это приблизилось бы к реплею; добавляется поправкой спеки, когда
появится читатель): согласованность статусов с журналом; статусная согласованность вида
«`WAITING_HUMAN` требует кандидата»; внутренняя полнота решения (у решённого ревью есть
`decided_by`).

### 4.4. Постусловие

Возвращённый Run **неотличим** от сохранённого:

- те же скаляры, те же `tasks`/`artifacts`/`human_reviews`/`evaluations`/`analytics_records`, тот
  же порядок `events`; `restored.snapshot == snapshot`;
- то же поведение: те же допустимые/запрещённые переходы (RUN_SPEC §4), те же доменные ошибки, те
  же ворота одобрения артефакта (Human Review + последняя Evaluation `PASSED`, ADR-0007/0018);
- **терминал остаётся терминалом** — обеспечивается таблицей переходов (у `COMPLETED`/`FAILED`
  нет исходящих рёбер), отдельной проверки не требует;
- продолжение (`open_task`/`create_artifact`/`open_human_review`/`open_evaluation`/
  `record_analytics`) использует восстановленные счётчики и **не создаёт коллизий id**.

## 5. Чего `Run.restore` НЕ делает

- **Не переигрывает** события/переходы (нет реплея; ADR-0015).
- **Не совершает** переход и не эмитит событий.
- **Не знает** о хранилище/сериализации/атомарности — это `RunStore`.
- **Не гарантирует** отсутствие двух «живых» Run с одним `run_id` — это ответственность
  вызывающего/хранилища (RUN_SPEC §4a, второй класс ошибки), а не самой фабрики. `restore`
  обеспечивает лишь допущение по инвариантам §5.

---

## 6. Связь с `RunStore` (для полноты, вне предмета контракта)

- `RunStore.save(run)` наблюдает Run через `Run.snapshot` (§3.2) и сохраняет снимок целиком.
- `RunStore.load(run_id)` читает снимок и вызывает `Run.restore(snapshot)` → восстановленный Run
  либо доменная ошибка (`RunRestorationError`), либо `None` для неизвестного `run_id`.
- Реализация MVP — `SqliteRunStore` (ADR-0024): формат, транзакции и отображение ошибок — там.

Проводка (когда сохранять) — Composition Root и Content Director (Этап 7), не этот документ.
