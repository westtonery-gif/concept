# ADAPTER_ACCEPTANCE.md — Критерии приёмки контрактов слоя адаптеров

> Приёмка `ADAPTER_SPEC.md` (по `ADR-0023`). Каждый критерий фальсифицируем: при неверной
> реализации соответствующий тест падает. Идентификаторы используются в именах тестов
> (`tests/test_adapter_contract.py`, `tests/test_domain_error.py`).
>
> **Статус:** Accepted. **Дата:** 2026-09-15.

---

## 0. Соглашения

- Проверяются контракты, а не реализации: реализаций на этом шаге нет. Соответствие протоколам
  доказывается mypy --strict на минимальных тестовых конформерах.
- Проверки границ читают исходники пакета (`ast`), а не поведение.

## 1. Контракты (ADC) — `tests/test_adapter_contract.py`

| ID | Сценарий | Ожидание |
|---|---|---|
| ADC-01 | Форма каждого протокола | ровно объявленные публичные методы; имена и виды параметров как в спеке (одиночный аргумент — positional-only; `run_id`/`status` у `report_status` — keyword-only); тестовые конформеры проходят mypy --strict |
| ADC-02 | `IncomingBrief`: пустой/пробельный/не-строковый `brief_ref` или `body` | `ValueError`; корректный — неизменяем |
| ADC-03 | `ReviewPackage`: пустые `run_id`/`review_id`/`brief`; кандидат другого Run; кандидат не `CANDIDATE`; `qa_flags` не кортеж / с пустым флагом | `ValueError`; корректный (с флагами и без) — неизменяем |
| ADC-04 | `ReviewDecision`: `PENDING`; строка вместо `ReviewStatus`; пустая причина | `ValueError`; три терминальных решения принимаются; неизменяем |
| ADC-05 | Контракты и неизменённый API Run | Run создаётся из `IncomingBrief`, сохраняется в `RunStore`, его статус — в `BriefBoard`, его `analytics_records` — в `AnalyticsSink`; `ReviewDecision` передаётся в `Run.submit_review` без преобразований (mypy) |

## 2. Границы (ADB) — `tests/test_adapter_contract.py`

| ID | Сценарий | Ожидание |
|---|---|---|
| ADB-01 | Импорты модулей `adapters/` | только разрешённый чистый stdlib, `domain.*`, `adapters.*` |
| ADB-02 | Импорты всех модулей вне `infrastructure/` | нет сторонних пакетов и сетевых/файловых модулей stdlib — ядро не ходит наружу напрямую |
| ADB-03 | Кто импортирует `infrastructure` | только Composition Root |
| ADB-04 | Импорты `domain/` | только stdlib и `domain.*` — домен не знает об адаптерах |
| ADB-05 | Идентификаторы в `adapters/` | нет имён поставщиков (`notion`, `google`, `gdoc`, `anthropic`, `claude`, `n8n`, `sql`) |
| ADB-06 | Модули пакета | все просканированы и импортируются по отдельности |

## 3. Ошибки (ADT) — `tests/test_domain_error.py`

| ID | Сценарий | Ожидание |
|---|---|---|
| ADT-01 | `RunStoreError`, `BriefBoardError`, `ReviewDeskError`, `AnalyticsSinkError` | технические — **не** `DomainError` |

## 4. Что приёмка НЕ проверяет

Поведение реализаций — оно проверяется против каждой реализации отдельно: Storage Adapter — §5,
заглушки (идемпотентность `publish`/`report_status`/`export`) — §6, проводка `RunStore` в Content
Director — §7, Notion Adapter — §8, обратная запись статусов — §9. Проводку остальных адаптеров; реальные Notion/Google Docs/аналитику (Этапы 9–10,
13–14).

## 5. Storage Adapter (STO) — `tests/test_sqlite_run_store.py` (ADR-0024)

Проверяется `SqliteRunStore` на настоящем файле базы; «перезапуск» — второй экземпляр store на том
же файле. Испорченные строки пишутся в базу напрямую.

| ID | Сценарий | Ожидание |
|---|---|---|
| STO-01 | Run сохранён, затем загружен другим экземпляром store («перезапуск») | тот же снимок; `Decimal`-стоимость и смещение времени точны; реализация проходит mypy как `RunStore` |
| STO-02 | `load` неизвестного `run_id` (пустая база; база с другим Run) | `None` |
| STO-03 | повторный `save` изменённого Run | хранится новая истина; строка одна |
| STO-04 | повторный `save` без изменений, в т.ч. только что загруженного Run | хранимый документ тот же, байт в байт |
| STO-05 | загруженный Run продолжается и сохраняется снова | следующие id без коллизий; после новой загрузки — та же истина |
| STO-06 | `save`/`load` при чужой блокировке базы | `RunStoreError`; прежняя истина цела |
| STO-07 | база не открывается (каталог; нет каталога; файл не SQLite) | `RunStoreError` на `save` и на `load` |
| STO-08 | хранимый документ испорчен (не JSON; чужая или булева версия формата; лишний, недостающий или неверно типизированный ключ; неизвестный статус или тип события; битая стоимость) или строка содержит другой Run | `RunStoreError` |
| STO-09 | хорошо сформированный документ, который Run не допускает; значение, которое отвергает домен | `RunRestorationError`; доменная ошибка — без маскировки в `RunStoreError` |
| STO-10 | кодек: снимок → JSON-текст → снимок | равный снимок |
| STO-11 | реестр событий кодека | совпадает со всеми классами событий журнала домена; незарегистрированное событие валит `save` (`RunStoreError`), ничего не записав |

## 6. Заглушки (STB) — `tests/test_in_memory_adapters.py` (ADR-0025)

Проверяются `InMemoryBriefBoard`, `InMemoryReviewDesk`, `InMemoryAnalyticsSink` против
ADAPTER_SPEC §5–§7 и правил ADR-0025 §3 для случаев, о которых контракт молчит. Run ведётся только
через публичный API Run.

| ID | Сценарий | Ожидание |
|---|---|---|
| STB-01 | каждая заглушка как свой протокол; импорты модуля | проходят mypy --strict как `BriefBoard` / `ReviewDesk` / `AnalyticsSink`; импортируют только чистый stdlib контрактов, `domain.*`, `adapters.*` |
| STB-02 | `fetch_brief`: готовый бриф; неизвестный; не готовый; перезаписанный готовым / снова не готовым | бриф как подан; `None`; `None`; новая версия; `None` |
| STB-03 | `report_status`: последовательность статусов с повторами; неизвестный бриф | история по порядку, повтор последнего отчёта не дублируется; `BriefBoardError`, ничего не записано |
| STB-04 | `publish`: тот же пакет дважды; другой пакет под тем же `review_id` | непустое место, то же место, одна копия; `ReviewDeskError`, остаётся первый |
| STB-05 | `fetch_decision` / `decide`: ждущее ревью; решённое; неопубликованное; второе другое решение; повтор того же | `None`; решение; `ReviewDeskError` на чтение и на решение; `ReviewDeskError`, остаётся первое; ничего не меняется |
| STB-06 | `export`: пересекающиеся и повторные пакеты, пустой пакет; другая запись под доставленным `record_id` или дважды в одном пакете | каждая запись один раз, в порядке первой доставки; `AnalyticsSinkError`, пакет не доставлен ни частично |
| STB-07 | бриф → Run → статусы → ревью → решение → `Run.submit_review` → `APPROVED` → `COMPLETED` → экспорт дважды, через заглушки и неизменённый API Run | Artifact `APPROVED`; на доске `WAITING_HUMAN`, `COMPLETED`; в стоке ровно записи Run |

## 7. Проводка Storage (SWR) — `tests/test_storage_wiring.py` (ADR-0026)

Проверяется `ContentDirector` со store: точки фиксации (ADR-0026 §2) и продолжение восстановленного
Run (§3). «Падение процесса» — исключение, брошенное исполнителем, оценщиком или store сразу после
записи; «перезапуск» — новый `SqliteRunStore` на том же файле и новый Director. Исполнители и
оценщик детерминированы и считают свои вызовы.

| ID | Сценарий | Ожидание |
|---|---|---|
| SWR-01 | двухшаговый прогон со store, без QA и с QA | ровно по одному `save` на точку фиксации, в порядке таблицы ADR-0026 §2; последний сохранённый снимок равен итоговому Run |
| SWR-02 | в момент каждого вызова исполнителя / оценщика | в store уже лежит его Task в `RUNNING` с тем же входом / его `PENDING` Evaluation; ни в одном сохранённом снимке нет `SUCCEEDED` Task без Output или Output без Artifact |
| SWR-03 | тот же прогон без store | итоговый снимок тот же, что со store |
| SWR-04 | процесс падает во время вызова исполнителя второго шага; перезапуск, `resume_workflow` | первый шаг не выполняется снова; второй выполняется на сохранённом входе, `attempt_count` = 2; Run `COMPLETED`; id без коллизий |
| SWR-05 | процесс падает сразу после k-й фиксации, для каждого k; перезапуск, `resume` | Run `COMPLETED` с тем же содержимым Artifact, что без падения; всего ровно по одному вызову исполнителя на шаг и один вызов оценщика |
| SWR-06 | процесс падает во время вызова оценщика; перезапуск | та же `PENDING` Evaluation получает вердикт (второй не открывается); `PASSED` → `COMPLETED` |
| SWR-07 | `resume` Run в `WAITING_HUMAN` с эскалационным ревью; `COMPLETED`; `FAILED` | ничего не вызывается и не меняется; нового ревью нет |
| SWR-08 | `resume` Task в `RUNNING`, чьи попытки исчерпаны | исполнитель не вызывается; Task `FAILED` с `RESUME_LIMIT_REASON`; Run `FAILED` |
| SWR-09 | `resume` Run, чьи Task не совпадают с планом (другой шаг/роль; Task больше, чем запросов) | `RunResumptionError`; Run не изменён, ничего не сохранено |
| SWR-10 | `resume` только что созданного Run; `execute` восстановленного | как `execute`; `execute` по-прежнему отвергает не-`CREATED` Run (`InvalidTransitionError`) |
| SWR-11 | `build_run_store`: переменная не задана / пустая / задана; `compile_runtime(..., store=)` | `.omemo/runs.sqlite3` / то же / указанный путь, каталог создан; собранный Director сохраняет Run |

## 8. Notion Adapter (NBB) — `tests/test_notion_brief_board.py` (ADR-0040)

Проверяется `NotionBriefBoard` через его настоящий HTTP-код против локального HTTP-сервера,
играющего Notion (страницы, блоки, записанные запросы). Сеть за пределами `127.0.0.1` не
используется; ни одного мока ниже адаптера.

| ID | Сценарий | Ожидание |
|---|---|---|
| NBB-01 | адаптер как контракт; каждый запрос | проходит mypy --strict как `BriefBoard`; `Authorization: Bearer <token>`, `Notion-Version: 2022-06-28`, JSON-тело у `PATCH` |
| NBB-02 | готовая страница базы с текстовыми и нетекстовыми блоками на нескольких страницах выдачи | `IncomingBrief(ref, body)`: текстовые блоки по порядку, по строке; нетекстовые пропущены; прочитаны все страницы выдачи |
| NBB-03 | пустой ref; `404`; архив; корзина; другая база (id с дефисами/регистром — та же база); не готов; пустое значение; пустое тело | `None`; для пустого ref запрос не отправлен; та же база в другом написании — бриф |
| NBB-04 | свойство готовности отсутствует / не `status`/`select`; ответ `400`/`401`/`429`/`500`; не JSON; `results` не список; сервер недоступен; таймаут | `BriefBoardError` |
| NBB-05 | `report_status` на странице базы, повтор того же отчёта | `PATCH` пишет `status.value` и `run_id` в два `rich_text`-свойства; повтор даёт то же состояние страницы |
| NBB-06 | `report_status`: пустой ref; `404`; архив; корзина; другая база; свойство отсутствует / не `rich_text`; сбой `PATCH` | `BriefBoardError`; во всех случаях, кроме сбоя `PATCH`, `PATCH` не отправлен |
| NBB-07 | ref с `/`, `?`, `#`, `..` | кодируется целиком в один сегмент пути; другой эндпоинт не адресуется |
| NBB-08 | `notion_settings_from_env`: все переменные; отсутствующие/пустые; токен | настройки; `BriefBoardError`, в сообщении имена всех отсутствующих, без значений; токена нет ни в `repr` настроек, ни в сообщениях ошибок |

## 9. Обратная запись статусов (BSR) — `tests/test_brief_status.py` (ADR-0041)

Проверяется `BriefStatusReporter` вокруг настоящего `ContentDirector` и `SqliteRunStore` (или
записывающего store) с `InMemoryBriefBoard`; доска-двойник, где нужно, отказывает на заданном
статусе и в момент каждого отчёта смотрит, что уже лежит в store. Исполнители и оценщик
детерминированы.

| ID | Сценарий | Ожидание |
|---|---|---|
| BSR-01 | двухшаговый прогон через репортёр: без QA; с QA `PASSED`; шаг падает | на доске ровно `queued`, `running`, `waiting_qa`, `waiting_human`, `completed` / то же / `queued`, `running`, `failed`, каждый один раз, с `run_id` Run; итоговый Run и сохранённый снимок те же, что без репортёра |
| BSR-02 | в момент каждого отчёта | store уже хранит Run в этом статусе |
| BSR-03 | QA `FLAGGED` → `CHANGES_REQUESTED` → перезапуск (новый store на том же файле, новый репортёр) → `resume_workflow` | до перезапуска: … `waiting_qa`, `waiting_human`; после: `running`, `waiting_qa`, `waiting_human` |
| BSR-04 | доска отказывает (`BriefBoardError`) на `running`; отдельно — на `waiting_human` (конец прогона), потом снова доступна: `save` в том же статусе, затем `sync` | прогон доходит до `completed` с тем же снимком, что без отказа; `running` не показан, остальные показаны; ровно одна попытка, один `FailedReport(run_id, running, …)` и один `WARNING`; во втором случае `save` не повторяет, `sync` показывает `waiting_human` |
| BSR-05 | `save` store падает (`RunStoreError`) | ошибка пробрасывается; отчёта нет |
| BSR-06 | повторные `save` без смены статуса; `sync` показанного; новый репортёр, `sync` Run в `waiting_human` | один отчёт; ничего нового; один отчёт `waiting_human` |
| BSR-07 | доска бросает не `BriefBoardError`; `load` | исключение пробрасывается; `load` возвращает то же, что store |
| BSR-08 | `BriefStatusReporter` как контракт | проходит mypy --strict как `RunStore` |
